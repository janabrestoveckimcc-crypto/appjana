# ARCHITECTURE.md

How relAI is built. WHAT it does is defined only in `docs/SRS.md`; this file never overrides it. If the two seem to conflict, stop and ask.

## 1. Principles
- **KISS.** The simplest code that passes the SRS section 12 checks. No abstraction until the second real use. No preparation for roadmap items (R1–R6).
- **No new dependencies** beyond section 2. If one seems necessary, ask first.
- **Real or nothing.** No mock functions, no fake data shown as real, no buttons that do nothing, no placeholder graphics (SRS 1). Designer files come from the team (section 3); if one is missing, stop and ask.
- **Small code.** Max 4 parameters (use an object beyond that), nesting depth max 3, no nested ternaries, no `any`, explicit return types on services and shared functions.

## 2. Stack
- Frontend: Vite, React, TypeScript, Tailwind, shadcn/ui, React Router, TanStack Query, React Hook Form, Zod. date-fns only for display formatting.
- Backend client: `@supabase/supabase-js`, created once in `src/lib/supabase.ts` and typed with `src/lib/database.types.ts` (generated by the Supabase CLI, never edited by hand).
- Backend: one Supabase project only (Postgres, Auth, Storage, Edge Functions, `pg_cron` + `pg_net` for the hourly job), managed with the Supabase CLI (`supabase` as a dev dependency, run with `npx supabase`). Migrations live in `supabase/migrations/`.
- Edge functions run on Deno: relative imports include the `.ts` extension; npm packages only through `npm:` specifiers, pinned to the same major version as in `package.json` (e.g. `npm:zod@<major>`). `supabase/functions` is excluded from the app's `tsconfig`.
- Hosting: Vercel, static Vite build, auto-deploy from `main`. `vercel.json` rewrites every route to `/index.html` (deep links from notifications, SRS 7.4) and sets `Cache-Control: no-cache` on `/sw.js` and the manifest.
- Environment: the frontend reads only `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (anon or publishable key, public by design) and `VITE_VAPID_PUBLIC_KEY` (F17). Local values in `.env.local` (git-ignored); names only in `.env.example`. Edge function secrets only in Supabase Secrets (DATA_SECURITY.md section 5).
- AI: Gemini REST API via plain `fetch` in `_shared/gemini.ts`. No SDK, no LangChain.
- Time zone: `Intl.DateTimeFormat` with `Europe/Zagreb`. No time zone library.
- PWA: hand-written manifest (SRS 10) and `public/sw.js` only as described in SRS 7.4 and PUSH.md. No PWA plugin (no `vite-plugin-pwa`, no Workbox), no caching.
- Languages: Croatian (default) and English (SRS 10) via our own small dictionary in `src/lib/i18n/` (`hr.ts`, `en.ts`, a `useT()` hook, `Intl` for dates and numbers). No i18n library.
- Tests: Vitest, run in Node on the pure `_shared/rules*.ts` files only (see TESTING.md).

## 4. Layers and dependencies
- Frontend: `page → feature component → hook → service → backend`. Components never import the backend client. Services select explicit columns, never `select('*')`.
- Edge functions: `index.ts` handles CORS (including `OPTIONS`), auth (`_shared/auth.ts`), Zod input validation and error mapping only; logic lives in `_shared/` or next to `index.ts`.
- `_shared/rules.ts` is the single source of truth for date and HP calculations. The frontend never recalculates HP; it displays values from the database.
- Imports flow one way: `pages → features → components/shared, lib`. Features never import from each other; move shared code to `components/shared/` or `lib/`. `_shared/` never imports from a function folder. No circular imports.
- `src/` and `supabase/functions/` never import from each other. The only exception: Vitest imports `_shared/rules*.ts`.

## 5. Naming
- Folders and non-component files: dash-case with a role suffix (`documents.service.ts`, `use-tasks.ts`, `zagreb-time.ts`). Components: `PascalCase.tsx`. Named exports only (except where tooling requires default).
- Code, tables and columns in English. Every UI text comes from the i18n dictionary, in both `hr` and `en`; no hard-coded strings in components (SRS 10). Enum values exactly as in SRS 8.1; their labels are translated in the dictionary.

## 6. Errors and UI states
- Every edge function returns errors in one shape: `{ "status": 400, "code": "DOC-0001", "detail": "user-safe message in the user's language", "reason": "OPTIONAL_MACHINE_CAUSE" }`. Codes are stable and defined in `_shared/errors.ts`. The frontend branches on `code`, never on message text.
- No empty `catch`. Never show stack traces or system details to the user.
- Every async view has loading, empty, error (with retry) and success states (SRS 10).

### Direct push implementation (user-authorized, 2026-10-08)
Server-only npm:web-push@3.6.7 creates encrypted, VAPID-signed request details; native fetch performs delivery. Deno typecheck and deployed authenticated configuration verified. Actual push delivery still needs a subscribed browser/device test. VAPID private key remains exclusively in Supabase Secrets. Frontend reads the public key from send-push config; only Supabase URL and publishable key are build environment variables.
